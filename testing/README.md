# Tests without test doubles

The landmines lint rules (`.oxlintrc.json`) refuse `vi.mock`, `vi.fn(impl)`, `mockReturnValue` and the like, `vi.stubGlobal`, and patched globals. Use the real module. Use MSW for the network. A spy may only watch. The rules also refuse fixed sleeps, retries and raised timeouts. In test code they refuse comments and annotated return types. Put the reasons in the commit message.

Lint each file you touch: `pnpm exec oxlint <files>`. It prints nothing when the file is clean.

## Where a test runs

The file name alone picks the runner. Do not add `// @vitest-environment` comments.

| Name                   | Project   | Runs in                                             | Use it for                                                                                                                     |
| ---------------------- | --------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `*.int.test.ts`        | `node`    | Node, with the database                             | Payload, server actions, routes                                                                                                |
| `*.unit.test.ts(x)`    | `node`    | Node                                                | Pure code, server code, emails rendered to HTML                                                                                |
| `*.dom.test.ts(x)`     | `dom`     | jsdom                                               | Components that need no layout, no observers and no media queries                                                              |
| `*.browser.test.ts(x)` | `browser` | Headless Chromium (Vitest browser mode, Playwright) | Components that need layout, `ResizeObserver`, `IntersectionObserver`, `matchMedia`, container queries, popovers or animations |

`pnpm exec vitest run` runs all three projects. `pnpm test:unit` runs everything except `*.int.test.ts`. Run one project with `--project browser`. The browser project uses the Chromium that Playwright caches (`pnpm exec playwright install chromium` if it is missing).

## Move a test from jsdom to the browser

1. `git mv x.dom.test.tsx x.browser.test.tsx`.
2. Delete the stand-ins for what Chromium has: `ResizeObserver`, `IntersectionObserver`, `matchMedia`, `scrollIntoView`, `getAnimations`, `animate`, `showPopover` and `hidePopover`. In Chromium a plain assignment such as `globalThis.ResizeObserver = class {}` replaces the real one, so a leftover stub silently turns the browser off.
3. For a phone layout, call `await page.viewport(390, 844)` (`import { page } from 'vitest/browser'`). For a reduced-motion branch, call `await emulateMedia({ 'prefers-reduced-motion': 'reduce' })` from `media.test-utils` (checked with a scratch test, no exemplar yet). The setup puts the 1280 × 800 viewport and the media back after each test.
4. Delete mocks of `@/lib/use-narrow` and `@/components/calendar/ui/use-narrow`. The real hooks read the real viewport and the real container queries. Real CSS also hides things: a `getByRole` that found an element in jsdom can miss it in Chromium when the stylesheet hides it at that width. Size the viewport to the layout you test.
5. To watch a call, use `vi.spyOn(object, 'method')` with no implementation. It calls through.
6. Change the URL with a relative URL (`history.replaceState(null, '', '#x')`). The test runs in an iframe of the Vitest page. Do not send it to another path.
7. A test that reads a file from disk (`node:fs`) checks source, not rendering. Move that test to a `*.unit.test.ts`.
8. Run the file, then lint it.

A browser test must not import server code, even through a component. If one file reaches `payload` or `@payload-config`, Vite's dependency scan fails and every browser test fails with it. See [Components that call server actions or Payload](#components-that-call-server-actions-or-payload).

Exemplars: `src/components/course/course-syllabus.browser.test.tsx` (`ResizeObserver`), `src/app/(frontend)/[locale]/study/[slug]/course-view-time.browser.test.tsx` (`IntersectionObserver`), `src/components/person-profile-block.browser.test.tsx` (`matchMedia`, a phone), `src/components/calendar/ui/calendar-views.browser.test.tsx` (container queries, server markup and hydration), `src/components/calendar/ui/use-narrow.browser.test.tsx` (the calendar's width flags).

## Storage

Vitest never reads storage from `.env`, which holds the production R2 bucket. `vitest.config.mts` takes the `R2_*` settings as one set from `testing/local-env.ts`: the shell's when it exports `R2_ENDPOINT` (CI and the search test do), otherwise the lines of `.env.development.local` (the local RustFS). The config refuses to start, and `vitest.setup.ts` refuses to run, when `R2_ENDPOINT` or `R2_PUBLIC_URL` is not a local host.

## The network: MSW

Call `mockNetwork(...handlers)` once at the top of the file or the `describe`. Add per-test handlers with `network.use(...)`. They reset after each test.

- Node (`*.unit.test.ts`, `*.int.test.ts`, `*.dom.test.tsx`): `mockNetwork` from `msw-node.test-utils`.
- Browser: `mockNetwork` from `msw-browser.test-utils`. The browser project serves `node_modules/msw/lib` as its public folder, so the worker file never enters `public/` or the production build. The app's own `public/` files are not served in browser tests.

Both start MSW with `onUnhandledRequest: 'error'`, and both fail the test in `afterEach` for each request that no handler answered, even when the code caught the error. So a test proves that a request did not happen by having no handler for it. Requests for scripts, styles and other assets (MSW's `isCommonAssetRequest`) are not counted. Answer with `HttpResponse.json`, `HttpResponse.html`, `new HttpResponse(null, { status: 302, headers })`, or `HttpResponse.error()` for a network failure.

- In jsdom, a relative URL such as `fetch('/api/x')` resolves against `http://localhost:3000/`, and a handler for `/api/x` answers it (checked with a scratch `.dom.test.tsx`).
- An int test that also calls a local service the test owns (Typesense, RustFS) lets those requests through by origin: `http.all('http://localhost:8108/*', () => passthrough())` (checked against the local Typesense). Do not pass through a whole public origin.
  The handlers exist as `payloadServices` (`fan2-payload-services.test-utils`: Typesense, and a 204 for Payload's telemetry) and `localServiceHandlers` (`fan4-local-services.test-utils`: the storage bucket, Typesense and telemetry). The storage handler lets uploads through to `R2_ENDPOINT`, which the runner keeps local (see Storage).
- In the browser, `next/image` asks Next's image optimizer, which a test has no server for. Add `nextImages()` from `msw-browser.test-utils`: every image is one pixel.
- Email: Payload builds its real Resend adapter when `RESEND_API_KEY` is set, and an MSW handler for `https://api.resend.com/emails` records each send. `captureResendMail` (`fan2-resend.test-utils`) and `resendInbox` (`fan1-resend.test-utils`) both do this.
- Web push: `pushDevice()` (`fan2-web-push.test-utils`) makes a real P-256 subscription and decrypts what the server sent to it. Exemplar: `src/lib/push/push-send.int.test.ts`.

Exemplar: `src/lib/event-place.unit.test.ts`.

## Components that call server actions or Payload

A browser test cannot load a server action or Payload, and a jsdom test can only reach them through `vi.mock`. So a component never imports an action. It gets the action from its host, in one of two ways.

**One action, one component: a prop.**

1. The component takes the effect as a prop, typed by what it needs: `save: (form: FormData) => Promise<SpacesWriteState>`. Import only types from the action's module.
2. A small connected component, in its own file, binds the real action: `<VotePoll {...props} save={(form) => voteSetAction({ status: 'ok' }, form)} />`. A server component can pass the action straight down instead. Keep an existing lazy boundary: load the connected file where the plain one loaded before.
3. The browser test plays the host: it passes a plain function that records its input and answers as the action does. This is the component's own interface, the same as the calendar's `onSave`. It is not `vi.fn(impl)`.

Exemplars: `src/components/space/connected-vote-poll.tsx`, `src/components/space/connected-space-head-actions.tsx`, and `src/components/admin/schedule-offer-dialog.browser.test.tsx` for the test.

**The calendar and schedule screens: one context.** Their actions (load, save, offer, publish, session view and edit, public calendar access) are called several components below the screen's root: the drawer's form, the edit drawer, the save and cancel hooks. Threading seven props through each layer ties every layer to every action, so the screens read them from one `ScheduleActions` value (`src/components/space/schedule-actions.tsx`) with `useScheduleActions()`.

1. The app mounts `ConnectedScheduleActions` (`connected-schedule-actions.tsx`, the real actions) at the root of each surface: the space page (its tabs and its drawer host), the post page, the public calendar page and the admin course calendar field. A screen rendered without it throws "Schedule actions are missing".
2. A test wraps the screen in `ScheduleActionsProvider` with `scheduleActionsHost()` from `schedule-actions.test-utils`. It records each call in `calls`, answers from `answers` (a test may replace one), and `reset()` puts both back. An action a test does not answer reports a refusal.
3. A plain function that takes some of the actions, such as `setSessionCancelled`, takes them as an argument. Its int test passes the real ones inside `runInRequest`.

A new action used by these screens goes into `ScheduleActions`. A new component outside them uses a prop.

Exemplars: `src/actions/space-calendar-edit.browser.test.tsx`, `src/components/calendar/public-calendar.browser.test.tsx`, `src/actions/use-schedule-save.dom.test.tsx` (a hook, with `renderHook`'s `wrapper`), `src/actions/public-calendar-edit.int.test.ts` (the real actions).

In both cases the action's own behavior gets an int test with `runInRequest` and the real Payload. The wiring between them is e2e.

Why not one way for both: a prop keeps a single-action component's interface visible in its type, and the context avoids a prop chain through components that never call the action. AGENTS.md calls a parameter with one caller surplus, but here the prop or the context is the only way the component can load in a browser at all. Moving every assertion to an int test or e2e loses the component's own states (busy, failed, retried), which only a rendered test can see.

## Server code with framework inputs

A route handler or server component that reads `@/env`, Payload or `next-intl/server` keeps that read in a thin outer layer and hands the values to a function that takes them as arguments. The test calls the inner function with real values.

- **Route handlers.** The route passes the secret, the request and the job: `handleSpacesCron(request, { secret, run })`. The test passes a real, harmless job. Exemplars: `src/lib/space-cron-request.unit.test.ts`, `src/lib/calendar-feed.unit.test.ts`.
- **`next-intl/server`.** The real `getTranslations` needs next-intl's `react-server` build and `src/i18n/request.ts`, which imports `next/root-params` (it throws outside Next's compiler). So the exported server component awaits `getTranslations` and `getFormatter` and renders a `…Body` that takes `t` and `format`. The test passes `serverTranslator(namespace, locale)` and `serverFormatter(locale)` from `fan4-server-intl.test-utils`: the real next-intl translator and formatter with the real messages. Exemplars: `src/components/events/event-attendance.unit.test.tsx`, `src/lib/public-event-card.unit.test.tsx`.

## Other patterns

- **A sleep that waits for a library's `setTimeout(0)`** (for example, Radix attaches its outside-click listener this way). Fake `setTimeout` around the trigger, run the one pending timer, then restore real timers. Check that the test fails without the timer run. Call `vi.useRealTimers()` in `afterEach` too. See the dialog exemplar.
- **Callback props.** `vi.fn()` with no implementation only records calls, so it is allowed. `vi.fn(impl)` is not. When the component needs the callback's answer, pass a plain function that records its input and returns the answer, as the host does.
- **Watching a real module.** `vi.mock(path, { spy: true })` keeps the real code and records calls. The rule allows it (checked with a scratch test: lint clean, real result, calls recorded).
- **Literal types without a return annotation.** Write `({ ... }) satisfies CalendarItem` where the annotation used to be. Without it, `tone: 'yellow'` widens to `string`.
- **Real pointer input in the browser.** A drag that needs trusted events goes through Chrome DevTools Protocol: `mouse.down`, `mouse.move` and `mouse.up` with `centerOf` or `visibleCenterOf` from `fan0-pointer.test-utils`. Clipboard permission: `setClipboardAccess('granted')` from `fan0-clipboard.test-utils`. Exemplars: `src/components/calendar/ui/calendar-edit.browser.test.tsx`, `src/components/calendar/calendar-feed-copy.browser.test.tsx`.
- **A link press the page leaves to the browser.** In Chromium an unprevented click on a link navigates the test frame away. To check whether the page took a press over, read `event.defaultPrevented` in a `click` listener on `window`, then prevent it. See `pageTookOver` in the public calendar test.
- **Animations under load.** Chromium runs the real enter animations, and a busy machine slows them. Assert visibility with `await waitFor(() => expect(x).toBeVisible())`, not right after the event that opened it.
- **Node 26 `localStorage`.** The config starts workers with `--no-experimental-webstorage`, so jsdom's real storage is the global. Do not redefine it.

## Not solved yet

- **Turnstile in the browser project.** `vitest.config.mts` sets `NEXT_PUBLIC_TURNSTILE_SITE_KEY` to an empty string for the browser project, as `playwright.config.ts` does, so forms there run with the honeypot alone: the real widget needs Cloudflare and waits for a token. Cloudflare's test site keys would keep the widget in the test.
- **Shared database.** All int tests share one local Postgres. A file that passes alone can fail in the full run when another file changes the same rows.
- **Duplicate helpers.** `payloadServices`, `localServiceHandlers` and inline handlers in six int tests answer the same services, and `captureResendMail` and `resendInbox` capture the same mail. Each pair should become one helper.
- **`testing/files/tiny.pdf`** has no xref table.

## Rejected

- Installing the missing browser APIs where lint cannot see them: jsdom's `beforeParse`, a custom environment file, or a non-test module. They are still stand-ins. The browser project replaces them.
- happy-dom. Its `ResizeObserver` and `IntersectionObserver` never fire (read in its source, not run), and 6 tests in 5 files failed on it (measured).
- Replacing a sleep with `setImmediate`, `requestAnimationFrame` or a retry loop. Each one guesses the time in a different way.
- Aliasing `next-intl/config` to a test-only request config.
- Making `@/env` tests set `window` to `undefined`. They run in node instead.
- Rerunning a browser test after "Vite unexpectedly reloaded a test". The browser project scans every browser test for dependencies before it starts (`optimizeDeps.entries`, `force: true`), so the reload does not happen.
