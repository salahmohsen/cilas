# Portal phase 1b: status and lists. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every reviewed document one status from one function, and give fellows, students and admins an Articles list and a Courses list in the portal that show that status, the next action and the work that waits on the reader.

**Architecture:** PR 1b-1 adds pure rules in `src/lib/` (`review-status.ts`, `reviewed-fields.ts`, `document-href.ts`), changes how the review hook keeps `review.request`, and lets an owner delete a declined, never-published item. PR 1b-2b adds the screens: the row, the list view, two pages under `(portal)/spaces/`, two items in `portalNav`, and the e2e.

**Tech stack:** Next.js 16.4.6 App Router, React 19.2.6, next-intl 4, Payload 3.91.0 (Postgres), Arc UI (`src/components/arc`), Vitest 4, Playwright 1.58.2, `@axe-core/playwright` (from phase 1a PR C).

**Spec:** `docs/superpowers/specs/2026-11-18-portal-design.md`: Status model, Lists, Document links, Navigation, Onboarding (empty states), Tests, Migrations, Phase 1b. The spec wins where they differ, except for the Deviations below.

A gated `find` as a student therefore returns the public archive. Every owner-list query adds the ownership `where` (`ownsViaAuthors(user)`, `ownsViaFellows(user)`), as `ownList` does (`src/access.ts:266-272`). - **Which row is which.** A draft save never writes the main row (`payload/dist/collections/operations/utilities/update.js:309-318`: `db.updateOne` runs only when `!isSavingDraft`). So only the main row says whether a document is live, and only the latest version holds the newest title. One function, `statusInputOf({ main, latest })`, builds `StatusInput` from the two rows. No caller builds `StatusInput` by hand. Each Interfaces block below names the row it takes.
- **Latest versions.** `createVersion` clears the old `latest` flag only where `updatedAt` is older than the new version (`@payloadcms/drizzle/dist/createVersion.js:48-56`), so two versions saved in one millisecond can both be `latest`. Every reader of latest versions keeps the newest `updatedAt` per parent.
- **Data access.** Every list read is a gated read (`user`, `overrideAccess: false`), per the spec's Data access rule. Every read that is not paged sets `pagination: false`, as `src/lib/review-queue.ts:31` does: with no `limit`, Payload returns 10 docs (`payload/dist/collections/operations/findVersions.js:83`, `sanitizedLimit = limit ?? (usePagination ? 10 : 0)`; `find` the same). A paged read sets `limit: PAGE_SIZE * pages` (L2). Every read names its `depth`: `0`, except the one populate read at `1`. With no `depth`, Payload populates to depth 2, and `findVersions` with no `select` returns whole versions (`findVersions.js:71-77`). Every read also names its `select`. No projection is new in 1b. Reads that populate use `depth: 1` with `select` and `populate` limited to the fields they need, as `src/lib/review-queue.ts:44-53` does (`depth: 0` populates nothing). A version `select` is `{ parent: true, version: { <field>: true, … } }`: field names as keys, and `parent` named, because `findVersions` adds `parent` only to `forceSelect` (U9). Version reads use `depth: 0`, because at `depth: 1` a selected `parent` populates the whole parent document. Two rows that `hasUnsentEdits` compares are read with the same `depth`, `locale` and field list, so a relationship is an id on both sides.

- How `loadList` reads (the invariants; the implementer picks the query code):
  - **Base `where`** (also the `total` count). Owner kinds: the ownership `where` (`ownsVia…(user)`); with no person, return `{ groups: [], total: 0 }` with no query. Admin: `or: [{ _status: { equals: 'published' } }, { 'review.status': { in: ['submitted', 'changes_requested', 'rejected'] } }, ownsViaAuthors|Fellows(user)]`, the last term only when the admin has a person. So an admin list leaves out other people's not-live rows at `draft` and at `approved` (Review Focus 4).
  - **The work set** holds the rows of the groups that load in full, the keys of `workKeys(kind)`. `loadList` builds it on every call, whatever `only` and `search` say, because each paged query leaves out all its ids (Review Focus 8). Its queries carry no search term. It has two kinds of candidates:
    - **Main candidates:** one gated `find` of main rows, `and: [base, { or: [KEY_WHERE[k].where for each main-row key k in workKeys(kind)] }]`, `select: { id: true }`, `depth: 0`, `pagination: false`. `KEY_WHERE.draft` holds the not-live `approved` state too, so an admin Unpublish row reads `draft` (with a warning) in In progress or Proposals. On an admin list the base `where` keeps only the admin's own not-live drafts, so the admin's own not-live `approved` row sits in In progress and `total` counts no row that no group shows.
    - **Copy candidates:** one gated `findVersions`. Its `where` is `or` of the `KEY_WHERE` rows of the version keys in `workKeys(kind)` when each of them has a row (admin, `fellowCourses`); else `LIVE_COPY`, the part those rows share (`ownerArticles`: `published_unsent` and `published_edits_declined` need a field compare, so `statusOf` decides). It reads `select: { parent: true }`, `depth: 0`, `pagination: false`. It has no ownership term and no other `parent.*` term (Global Constraints, Owner lists filter by owner).
    - **Rows:** for the candidate ids, one main read `and: [base, { id: { in: ids } }]` (a parent outside the base `where` drops out here) and one read of their latest versions (`parent in ids`, `latest: true`, newest `updatedAt` per parent), both in the two steps of Reads and the compare. `statusInputOf`, then `statusOf`, gives each key, and `groupOf` its group. A candidate whose group is paged (a `fellowCourses` course with a space; an owner's equal copy) leaves the work set. Work rows sort by the latest version's `updatedAt`, newest first.
  - **Space courses first** (`fellowCourses` only). Before the work set, one gated `find` of `spaces` (`select: { course: true }`, `depth: 0`, `pagination: false`) gives the reader's courses that have a space. Its ids give `hasSpace` to every `groupOf` call, the `id in` term of Teaching now and the `id not_in` term of Closed. A fellow listed on a course reads its space also when the course is not live: `factsFor` reads the course's fellows with `draft: true`, and `membershipOf` makes them moderators (`src/lib/spaces.ts`). A fellow who cannot read a space (spaces mode `off`: `loadReadState` gives no id) gets no id, so that course stays in Proposals or Closed.
  - **Co-authors.** Each owner sees what their version access gives them (U4; spec, Status model, Access). A co-author removed in the copy finds no copy: their row reads the live row alone, key `published`, in Published, until an admin approves the copy. A co-author added only in the copy owns no main row, so the main read drops the copy candidate and the row is not on their list until the approval.
  - **Paged groups.** `limit: PAGE_SIZE * pages[group]` (default 1 page), `page: 1`, `sort: '-updatedAt'` on the main row. Each `where` adds `id not_in` the work set's ids, all of them, also under a search, and is disjoint from the earlier paged groups by its own terms, so `only` can load one paged group with no other: `published`: `_status: published`. `teachingNow`: `_status: published`, or `id in` the space courses (Space courses first). `closed`: `_status: draft`, `review.status: rejected`, and on `fellowCourses` `id not_in` those space courses. Each page then reads the latest versions of its ids (`parent in ids`, `latest: true`, newest per parent, as in Reads and the compare) and builds each key with `statusInputOf`, so a paged row reads `published_unsent`, `published_edits_declined` or `published_removal_kept` when its copy says so. Every paged row's `groupOf` is its group (L3 tests it).
  - **Reads and the compare.** Every read of rows and their latest versions is two steps, so a page of up to 1000 rows does not load every body twice. Step one, for every id: the main rows with `select: { ...KEY_SELECT, tier: true, cover_image: true }`, and the latest versions with `select: { parent: true, version: { ...KEY_SELECT, cover_image: true } }` (U9), with `read: 'keys'`. Step one calls `statusInputOf` only to find the ids that need step two; it calls `statusOf` only on ids whose `draft` is null, where no compare runs. Step two, only for the ids whose main row is live and whose latest version is a draft copy (`statusInputOf` gives a non-null `draft`): the main rows with `select: statusSelect(collection)` and the latest versions with `select: { parent: true, version: statusSelect(collection) }`. `StatusInput` for those ids comes from the step-two rows, with `read: 'full'`; `statusOf` throws on a `keys` input that needs the compare (P15), so a step-one row cannot reach `hasUnsentEdits`. Each read is `depth: 0`, `locale: 'all'`, `pagination: false`, so a relationship (cover, authors, fellows) is an id on both sides. Covers come from one gated `find` of `media` (`id in` the shown rows' cover ids, `select: { ...mediaPopulate, sizes: true }`, `depth: 0`, `pagination: false`; media read access is `anyone`, `src/collections/Media.ts:47`). Owner names and the cycle come from one more main read of the rows shown, at `depth: 1`, `pagination: false`, with `select` and `populate` (`{ people: { name: true }, cycles: { season: true, start_year: true } }`).
  - **Courses.** One gated `find` of `sessions` (`course in` the shown ids, `select: { course: true, meetings: true, cancelled: true }`, `depth: 0`, `pagination: false`) gives `heldCount` per course, grouped by `course`. The read passes the course's own access (`throughRelation('course', readCourse)`, `src/collections/Sessions.ts:100`).
  - **Search.** A row matches when the title of its main row or of its latest version matches, because a row can show either (Deviation 8; a never-published draft's newest title is only in its versions, Review Focus 2). The work set is built with no search term (above), so a work row whose copy changed the title never falls into a paged group. `search` runs one gated `findVersions` (`latest: true`, `or: [{ 'version.title.en': { like } }, { 'version.title.ar': { like } }]`, `select: { parent: true }`, `depth: 0`, `pagination: false`; U8, U11) for `parentIds`. A work row stays when its id is in `parentIds` or in the ids of one gated `find` (`and: [base, { id: { in: workIds } }, { or: [{ 'title.en': { like } }, { 'title.ar': { like } }] }]`, `select: { id: true }`, `depth: 0`, `pagination: false`), so one `like` rule decides both. Each paged query adds `or: [{ 'title.en': { like } }, { 'title.ar': { like } }, { id: { in: parentIds } }]` beside its `id not_in` all the work ids. `like` keeps `%` and `_` as wildcards: they only widen a match over rows the reader may read. `only` returns that one group. Neither changes `total`.
  - Groups with no rows are dropped. A group's `total` comes from the query's `totalDocs` for a paged group, from the row count for a work group.
