## Decision log (structural)

Each problem, then its fix.

- P1. The review queue (`review-queue.ts:30-56`) and `waitsOn` are two rules for "what waits on an admin": the queue reads raw `review.status`, `KEY_WHERE` adds `NOT_LIVE` and `LIVE_COPY`. A count from one and a list from the other can disagree. And a count of candidates with a list of the rows that pass `statusOf` can disagree too (code review M-1). Fix: one set per source, `waitingSet` (the candidates of the matching 1b list, version parents kept only when live, whose main row is inside the base, kept when their keys-only `statusOf` key waits on the side, N2). For the admin the base is 1b-1's `ADMIN_VISIBLE`, the candidate keys are the 1b admin list's (`ADMIN_LIST_KEYS`, pinned to `workKeys('admin')`) and the candidate read is 1b-2a's, moved, so Needs you, the queue and the 1b admin list's Needs you group are one rule, except for an admin's own not-live row that the list's `owned` term reads (Deviation 21; P30, P38).
