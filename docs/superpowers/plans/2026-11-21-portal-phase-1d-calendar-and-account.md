# Portal phase 1d: calendar and account. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every signed-in reader a Calendar tab in the portal that starts on their own courses and the public events, and one account page in the portal for their profile, sign-in and notifications. The old `/settings` and `/profile` addresses keep working as redirects.

**Architecture:** Three PRs, and a fourth only when phase 1c's Home is not on `main` when 1d-3 opens. PR 1d-1 moves the account page into the portal shell at `/spaces/account`, turns `/settings` and `/profile` into redirects, points the account menu row at the new page, and adds the Sign-in group. PR 1d-2 adds the data of the Calendar tab with no screen: `readerCourseIds`, one gated read of the reader's own course meetings beside the cached public query (one shared builder, two sources), and the pure merge that gives the portal its legend kinds. PR 1d-3 adds the screen: one preset prop on the generic calendar, a path prop and a read-only prop on `PublicCalendar`, the `/spaces/calendar` page, the Calendar nav item, the `portal-calendar` e2e, and Home's **Open the calendar** when 1c-3 is on `main`. Else PR 1d-4 adds that link after 1c-3 merges.

**Spec:** `docs/superpowers/specs/2026-11-18-portal-design.md`: Phases (Phase 1d, and the target table rows Calendar, Home's **Open the calendar**, Profile and settings in the account menu), Calendar, Profile and settings (D5), Navigation, Architecture (Routes, Feature folders, Data access rule, Lazy loading rule), Accessibility baseline, UI skills, Tests. ## Legend preset

The spec says: "The plan reads the ui-sdk skill before it sets the legend preset." This plan read `SKILL.md` ("Default or controlled": `defaultValue` to start, or `value` with `onValueChange(value, details)` to control) and `toggle.md` at `0.1.0-beta.1`.

- The legend is `ToggleGroup` from `@ui-sdk/react/toggle` with `multiple`, `orientation="vertical"`, `aria-label={labels.legend}`, a controlled `value` (the kinds not in `hidden`) and `onValueChange(shownKinds)` that writes `hidden` (`calendar.tsx:823-837`). Each kind is a `Toggle` with `value={kind}`. A pressed toggle has `aria-pressed="true"` and `data-pressed` (`toggle.md`, "Data Attributes", "API Reference": `ToggleGroup.value?: T[]`, `defaultValue?: T[]`, `onValueChange?: (value: T[], details) => void`, `multiple?: boolean`).
- The group stays controlled. ui-sdk's own `defaultValue` would not reach `hidden`, which also filters the grid, the agenda, Up next and the hours (`calendar.tsx:211`, `:240`, `:500`, `:815`). So T1 adds one prop to `Calendar`, named in ui-sdk's style: `defaultHiddenKinds?: readonly string[]`, read once as the start of `hidden` (`useState(() => new Set(defaultHiddenKinds))`). After mount the reader owns the legend. A change of the prop after mount does nothing (ui-sdk's "default" contract).
- **Hidden kinds outside the legend stay hidden (code review H-1).** The legend lists only the kinds of the loaded items (`legend = legendOf(session.items)`, `calendar.tsx:371`), and today `onValueChange` rebuilds `hidden` from the legend's kinds only (`:830-835`). So a preset kind with no item in the loaded range (a month with no other course) leaves `hidden` at the first toggle of any other kind, and its blocks come back in the next month. The view-mode `Calendar` is not remounted when the host loads a new range (it has no `key`, `public-calendar.tsx:216`; only the editor has one, `:203`), so `hidden` lives across months. T1 changes the rule: the new `hidden` keeps every kind of the old `hidden` that is not in the legend, plus the legend kinds not in `shownKinds`. In code: `new Set([...[...hidden].filter((kind) => !legendKinds.includes(kind)), ...legendKinds.filter((kind) => !shownKinds.includes(kind))])`. The public page passes no preset, so its behaviour changes only for a kind the reader turned off that later leaves and comes back, which now stays off (a fix there too).
- The public calendar passes nothing, so its legend starts with every kind on, as today.
- **The portal kinds and their cue (orchestrator decision; code review M-1).** `course:mine` ("Your courses") and `course:other` ("Other courses"), and the public event kinds unchanged (`event:<type>`, their type tones). Every one of the five tones is already used by an event type (`src/lib/calendar.ts:98-115`: `pink` is `workshop`, `neutral` is `other` and every type with no tone, `:121-122`), so no tone alone can set a course kind apart. So the course kinds get a shape cue that no event has, and colour is not the only signal (WCAG 1.4.1):
  - `CalendarItem` gains one optional field, `edge?: 'solid' | 'dashed'` (`src/lib/calendar-items.ts`, 1d-2 C3): "a bar on the start edge of the item's blocks, pills, agenda rows and legend swatch, in its tone's line colour". The calendar draws it from `data-edge` (1d-3 T1): a 3px `border-inline-start` in `var(--tone-line)`, `solid` or `dashed`; the legend swatch draws the same bar, also when its toggle is unpressed. It is not the hatch (that means cancelled, `calendar.module.css:362`, `:599`) and not `data-marked` (that means changed, `:365`, `:615`).
  - "Your courses": tone `pink`, `edge: 'solid'`. "Other courses": tone `neutral`, `edge: 'dashed'`. Events: no `edge`. So each course kind differs from every event by shape, and the two course kinds differ from each other by shape and by colour.
  - Contrast of the bar, `--calendar-<tone>-line` against the block's `--calendar-<tone>-fill` and against `--surface` (computed by this plan writer from the `foundation.css` values with an OKLab mix, `:49-68` light and `:199-218` dark; the builder measures again with better-colors): pink 5.74:1 and 6.91:1 light, 7.56:1 and 11.31:1 dark; neutral 4.21:1 and 7.13:1 light, 5.03:1 and 8.45:1 dark. Each is above 3:1 (WCAG 1.4.11, non-text contrast).
  - One tone and one edge per kind keeps the swatch true (P10): `legendOf` takes `edge` beside `tone` (T1).
- **The preset (Deviation 8).** `defaultHiddenKinds = presetHidden(ownIds)`, where `ownIds` is the set of course ids that the gated read returned meetings for (`new Set(own.flatMap((m) => (m.courseId === undefined ? [] : [String(m.courseId)])))`), not all of `readerCourseIds`. `presetHidden` gives `['course:other']` when the set is not empty, else `[]` (Deviation 3, Q1).
