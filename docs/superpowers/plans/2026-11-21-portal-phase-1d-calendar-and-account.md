> **For agentic workers:** use only pstack/poteto skills and playbooks, task by task; never superpowers or caveman (ledger, SKILLS RULE). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every signed-in reader a Calendar tab in the portal that starts on their own courses and the public events, and one account page in the portal for their profile, sign-in and notifications. The old `/settings` and `/profile` addresses keep working as redirects.

**Architecture:** Four PRs. PR 1d-1 moves the account page into the portal shell at `/spaces/account`, turns `/settings` and `/profile` into redirects, points the account menu row at the new page, and adds the Sign-in group. PR 1d-2 adds the data of the Calendar tab with no screen: `readerCourseIds`, one gated read of the reader's own course meetings beside the cached public query (one shared builder, two sources), and the pure merge that gives the portal its legend kinds. PR 1d-4 adds the Home card **This week** (operator, 2026-11-24, Deviation 11), the click test of **Open the calendar** (1c-3 built the link) and one calendar test fix.

## Legend preset

The spec says: "The plan reads the ui-sdk skill before it sets the legend preset." This plan read `SKILL.md` ("Default or controlled": `defaultValue` to start, or `value` with `onValueChange(value, details)` to control) and `toggle.md` at `0.1.0-beta.1`.

- The legend is `ToggleGroup` from `@ui-sdk/react/toggle` with `multiple`, `orientation="vertical"`, `aria-label={labels.legend}`, a controlled `value` (the kinds not in `hidden`) and `onValueChange(shownKinds)` that writes `hidden` (`calendar.tsx:823-837`). Each kind is a `Toggle` with `value={kind}`. A pressed toggle has `aria-pressed="true"` and `data-pressed` (`toggle.md`, "Data Attributes", "API Reference": `ToggleGroup.value?: T[]`, `defaultValue?: T[]`, `onValueChange?: (value: T[], details) => void`, `multiple?: boolean`).
- The group stays controlled. ui-sdk's own `defaultValue` would not reach `hidden`, which also filters the grid, the agenda, Up next and the hours (`calendar.tsx:211`, `:240`, `:500`, `:815`). So T1 adds one prop to `Calendar`, named in ui-sdk's style: `defaultHiddenKinds?: readonly string[]`, read once as the start of `hidden` (`useState(() => new Set(defaultHiddenKinds))`). After mount the reader owns the legend. A change of the prop after mount does nothing (ui-sdk's "default" contract).
- **Hidden kinds outside the legend stay hidden (code review H-1).** The legend lists only the kinds of the loaded items (`legend = legendOf(session.items)`, `calendar.tsx:371`), and today `onValueChange` rebuilds `hidden` from the legend's kinds only (`:830-835`). So a preset kind with no item in the loaded range (a month with no other course) leaves `hidden` at the first toggle of any other kind, and its blocks come back in the next month. The view-mode `Calendar` is not remounted when the host loads a new range (it has no `key`, `public-calendar.tsx:216`; only the editor has one, `:203`), so `hidden` lives across months. T1 changes the rule: the new `hidden` keeps every kind of the old `hidden` that is not in the legend, plus the legend kinds not in `shownKinds`. In code: `new Set([...[...hidden].filter((kind) => !legendKinds.includes(kind)), ...legendKinds.filter((kind) => !shownKinds.includes(kind))])`. The public page passes no preset, so its behaviour changes only for a kind the reader turned off that later leaves and comes back, which now stays off (a fix there too).

- **The portal kinds and their cue (orchestrator decision; code review M-1).** `course:mine` ("Your courses") and `course:other` ("Other courses"), and the public event kinds unchanged (`event:<type>`, their type tones).
